# Managed merchant configuration

`paymentconfig.Manager` owns direct-payment merchant administration. Both API and worker use the same PostgreSQL tables from migration 029 and the same `PAYMENT_CONFIG_KEY_FILE`. `PAYMENT_MODE=direct` requires exactly one of that key setting or the existing `PAYMENT_PROVIDERS_FILE`. Static-file mode stays strict and read-only in the administration API. Sandbox/disabled mode cannot contain either setting.

Managed startup accepts zero merchants. It requires a trusted HTTPS `PUBLIC_URL` origin with the standard HTTPS port, plus an existing absolute 32-byte AES key file. The file must be regular, owned by the running service UID, have owner read permission and no group/other or special mode bits, have one hard link, and contain no symlink in any path component. Provision a service-owned 0700 directory and 0600 key outside release directories. Runtime does not create, replace or rotate the key. Back up the original key privately together with the database and effective service configuration. A missing or incorrect key after installation fails closed; replacing it with a new key cannot decrypt existing revisions.

## Persistence and authority

Each revision encrypts all merchant metadata and credentials with AES-256-GCM, a fresh random nonce, and provider/version authenticated additional data. PostgreSQL stores the encrypted payload and the existing nonsecret merchant/application `ConfigurationID`; neither PEM nor APIv3 material is stored as plaintext. The singleton state row supplies a global optimistic revision across both channels. Updates hold the existing platform-administration advisory lock, check current `finance:write`, lock/check the revision, append the encrypted revision and write sanitized audit metadata in one transaction. Audit failure rolls back the merchant change. GET checks `finance:read` in its database read transaction. Product administrators, account owners, billing operators and service credentials gain no merchant-administration authority.

Current state uses each channel's latest revision. Recovery uses the latest credentials for every retained merchant/application identity, preserving accepted checkout bindings after a channel is disabled or its identity changes. Credential rotation within one identity updates that identity's recovery adapter. Keep trusted WeChat key IDs needed during a planned key overlap in `platform_key_ids`; omitted IDs are removed from the active trusted set. A supplied certificate is validated at save time, then stored as its explicitly trusted RSA public key so a future certificate-wrapper expiry does not prevent loading the configured key. Identity/revision history has no delete endpoint or automatic pruning.

API and worker load and validate the durable state at each financial operation. There is no last-known-good provider cache that can admit a new request after a failed database/key read. Configuration, key-read and decryption failures return bounded errors. Product capabilities and system status propagate failure rather than reporting an empty configured set. Already accepted receipts can finish ledger/fulfillment work without creating a new provider operation. Checkout replay returns its original durable checkout before testing whether the channel still accepts new sales. Original query, notification, close and refund select the retained `ConfigurationID`.

## Administration API

`GET /admin/v1/payment-providers` and successful `PUT /admin/v1/payment-providers/{wechat|alipay}` return `Status` from `types.go`:

- `version`, `mode`, `managed`, `store_ready`, `configured` and exactly two `providers`, ordered WeChat then Alipay.
- Each provider includes `id`, `enabled`, `configured`, public `app_id`, `merchant_id`, `seller_id`, `certificate_serial`, `platform_key_ids`, fixed `notify_url`/`return_url`, credential-presence booleans and `missing_fields`.
- Per-provider `configured` means valid installed credentials, even when disabled. Overall `configured` means at least one configured channel is enabled. `store_ready` confirms a successful current state read, not live acquiring acceptance. `managed=false` is read-only. An unknown static adapter reports `static_metadata_unavailable` in `missing_fields` rather than claiming metadata completeness.

PUT requires `expected_version`, `reason` with 1 to 2000 bytes after checking nonempty whitespace-trimmed content, and `enabled`. Public metadata replaces the current metadata. Write-only fields `private_key_pem`, `api_v3_key`, `public_key_pem` and values in `platform_public_keys` update credentials; omission retains them and empty/null values reject. WeChat `platform_key_ids` selects the complete trusted key set and `platform_public_keys` supplies replacements for those IDs. There are at most 16 trusted keys and each PEM is at most 64 KiB. APIv3 keys are exactly 32 bytes. Channel-inapplicable, unknown, duplicate and null fields reject. A blank disabled initial channel is allowed; other saves require a complete valid official adapter configuration, even when disabled.

Notify URLs are `PUBLIC_URL/payments/wechat/notify` and `PUBLIC_URL/payments/alipay/notify`; Alipay return is `PUBLIC_URL/`. The browser cannot set URLs, gateways or file paths. Alipay supports public-key mode. Construction validates configuration without contacting a provider. GET, success/error responses and audit contain no secret content or secret hash. Browser sessions use the existing same-origin/CSRF console path. System status and ordinary capabilities report channel names and readiness without merchant metadata.

Responses use `400 invalid_request`, `403 forbidden`, `409 conflict`, or `503 payment_configuration_unavailable`. A successful save returns the complete new status. The existing native-CREDIT policy/runtime gate remains independent. Saving merchant settings neither publishes a tariff nor proves a successful real payment.

## Local verification

Focused tests use disposable local PostgreSQL schemas, the existing local Formance fixture, generated RSA keys and controlled HTTP requests. They cover encrypted persistence, omission/empty secrets, authority, concurrent CAS, restart/two managers, audit rollback, key loss/corruption, AAD mismatch, read-failure propagation, console CSRF, original-identity signed callback/deduplication, and disabled-channel query/close/refund recovery. No test contacts an official merchant endpoint or performs a real payment/refund.
