# UniHub 首版设计

日期：2026-10-24。状态：业务方向已逐项确认；本文将该方向整理为可审阅的架构与实施边界。下文明确列出的实现建议未被记录为用户已确认的商业规则。

## 1. 已确认的业务范围

1. 建设多个自有产品共用的用户管理、充值、订阅、模型额度和运营后台。
2. 首版同时支持个人账户、企业团队账户；同一用户可以加入多个团队。
3. 各产品独立充值；可设置统一钱包，用户授权后自动向产品充值或续费。
4. 接入顺序为 SuperWagie、AgentWiki、llmrouter，随后璇玑、灵犀、虾说。
5. llmrouter 从 SuperWagie 接入阶段起提供平台模型能力；第三个产品接入节点是 llmrouter 自身产品入口接入，并非推迟模型服务。
6. SuperWagie、AgentWiki 等产品销售会员套餐；平台模型由 llmrouter 提供并统一消耗该付费账户的 llmrouter 模型额度。
7. 商业模式为包月/包年套餐包含模型额度；额度不足通过升级套餐或购买加量包扩容。
8. 套餐模型额度按月重置，不结转；年付也逐月发放。
9. 优先完成自有产品用户管理和充值计费；随后建设第三方账户连接，再扩展第三方 MCP/API 接入。后两项是后续方向，不纳入首版交付依赖。

## 2. 架构选择

| 路径 | 优点 | 代价 | 当前选择 |
| --- | --- | --- | --- |
| 以 Casdoor 为中心，扩展其内建余额与订阅 | 初始页面和账号能力集中 | 现有用户单余额不符合个人/团队、多产品资金与额度批次模型，深改身份项目 | 不采用为账务中心 |
| 直接以 Lago/Kill Bill/Flexprice 为商业核心 | 现成订阅、账单或计量能力 | 自动充值、钱包等存在商业版边界，仍需定制多账户及模型服务归属 | 暂不引入运行时 |
| Casdoor 身份 + 自有商业服务 + Formance 账本 + llmrouter 模型网关 | 每个组件职责明确，可保留现有产品业务；核心商业规则可控 | 需要自己建设订单、额度批次、授权与故障恢复 | 推荐，延续用户接受的组合方向 |

采用接口集成和独立服务部署，保留依赖许可证及版本信息。借鉴其他项目的业务模式，不直接拼接多套账务代码。

### 组件职责

- **Casdoor**：注册、登录、认证因素、账号安全、多应用 OIDC。正式产品隐藏其内建余额/收费入口。
- **UniHub API + Worker**：用户映射、团队、商品、套餐、订单、自动续费、现金钱包授权、模型额度批次、权益、审计、对账和产品 SDK。
- **Formance Ledger**：现金与模型额度资产的不可变分录、原子转移、冻结和结算；不承担用户登录与商业策略。
- **llmrouter**：模型供应商接入、路由、流式输出、可信用量、版本化模型费率、调用额度预占/结算适配器。
- **各业务产品**：本地资源、项目、空间和文档权限；验证购买权益并展示平台账户入口。
- **用户中心**：个人/团队切换、会员、统一钱包、各产品余额、模型额度来源、加量包、自动设置和账单。
- **运营后台**：产品和套餐配置、账户查询、订单、退款、异常恢复、用量、审计。

技术实现建议：Go 服务、PostgreSQL 业务库、React + TypeScript + Vite 前端。API/Worker 同代码库分别启动，首版使用 PostgreSQL outbox 和作业租约，不引入消息中间件集群。Formance 适配器固定稳定版 v2.4.16 评估；Casdoor 版本和镜像摘要在集成验证后锁定。

## 3. 核心领域和归属

### 用户与付费账户

`User` 表达登录身份，`IdentityLink(issuer, subject)` 映射外部身份。邮箱、手机号不作为跨产品归属主键。`BillingAccount` 分为 `personal` 与 `team`；钱包、订阅、订单、模型额度、退款全部归属它。

团队基础角色建议为 owner、admin、billing_admin、member。owner 管理所有权和账务；admin 管成员和产品访问；billing_admin 管充值、账单和自动授权；member 使用获准产品。所有权转移需要接收方确认，不能删除最后一个 owner。团队邀请必须由受邀身份接受，不能仅凭邮箱添加已登录权限。

产品使用请求固定 `acting_user_id`、`billing_account_id` 和 `origin_product_id`。运行中切换个人/团队不能改变已开始任务的付款方。个人与团队、不同团队之间不自动垫付；离职不改变历史账单、资金和退款归属。

### 现金与模型额度

| 资产 | 归属及用途 | 入账来源 | 减少方式 |
| --- | --- | --- | --- |
| 统一钱包现金 | 一个付费账户的共用资金 | 外部充值、关联退款 | 授权转入产品钱包 |
| 产品现金余额 | 一个付费账户 + 一个产品 | 直接充值、统一钱包划拨 | 购买/续费该产品会员或商品 |
| llmrouter 模型额度 | 一个付费账户的模型服务权益池 | 月度套餐发放、升级补差、加量包 | 经 llmrouter 确认的调用消耗、到期失效、退款撤回 |

模型额度不是现金，不允许反向兑换为钱包余额。套餐售价与包含额度是两个独立配置项。会员附赠额度可以由不同产品发放到同一付费账户的 llmrouter 额度池；来源产品、套餐、账期仍保留。

模型额度使用金额等价单位而不是固定 token 数的实现建议：llmrouter 用已登记价格版本把不同模型的 input/output/cache 等用量折算为额度。现金与额度使用不同资产代码；具体展示名称与兑换规则由商品配置决定，不隐含 1:1 兑换。

金额与额度使用定点整数，接口序列化为字符串，不使用二进制浮点记账。首版建议现金 CNY、内部精度 6 位，外部收款按支付通道允许的精度换算并校验；不得混币划拨。

## 4. 会员与模型额度批次

`PlanVersion` 保存会员功能、计费周期、价格、包含的月额度、适用个人/团队及席位规则。发布后不可修改已生成订单的快照；新价格使用新版本。

`Subscription` 归属付费账户和产品。月付与年付在订阅有效期内按月产生基础 `CreditGrant`，其唯一键为 `subscription_id + grant_period_start + base`。升级补额使用 `upgrade_order_id + grant_period_start`，加量包使用 `purchase_order_id + benefit_id`，允许同月连续升级而不重复执行同一升级。年付收到全年会员费后，不提前释放全年模型额度。

每个额度批次记录：来源产品、来源订单/订阅、适用付费账户、原始数量、可用数量、冻结数量、已用数量、撤回数量、失效数量、有效期、价格/规则版本。账户页面同时显示汇总余额与各批次明细。

Formance 的批次账户分录是数量权威；PostgreSQL 保存批次规则、业务关联及可重建的余额投影，不作为第二套可独立写入的额度余额。可用、请求预占、已用、失效/撤回使用独立账本账户；一次请求跨多个批次的分配在同一账本交易中提交。创建批次的发放命令也使用稳定引用，避免账本已发放而业务数据库重试又发一次。

每个批次必须满足 `原始发放量 = 可用 + 冻结 + 已用 + 撤回 + 失效`。有效区间和归属由业务库决定，资产数量由账本决定；预占同时验证这两个条件，不能仅凭账户总余额跳过批次有效期。

按订阅锚定日划分月度账期，内部时间使用 UTC；展示使用用户时区。月底缺少对应日时截到当月末，下月仍按原锚定日计算。任务补跑只补该订阅应有的当前有效批次，不因重复调度多发额度，不补发已经过期月份的可消费额度。

月度批次有效区间为 `[period_start, min(next_month_anchor, paid_through))`；`paid_through` 来自已付款订单的服务期限，补跑不能延长到期日。关闭自动续费不缩短已付款期限；退款终止则通过独立的有效期修订执行。年付最后一期不能越过已付服务终点。

建议扣减顺序：先到期的批次优先，同到期日按创建顺序，月度套餐额度先于同期限的付费加量包。已预占批次即使跨过到期点，也只能完成该次请求的结算；未使用部分释放后若批次已到期，进入失效账户，不能复活。

### 升级与加量包的实施建议

- 月/年套餐等级由后台配置；只允许购买已发布的商品，不编造实际销售价格。
- 升级先生成报价，明确差价、立即生效的权益、当前月增加额度、后续月额度和新的账期；用户接受报价后才付款。
- 不因升级重新发放已领取的当月全额，不重新延长已使用额度的有效期。升级补额根据新等级该周期应发总量减去该订阅该周期累计已发量计算，与当前剩余额度无关；订阅版本锁与唯一升级订单同时防止重复和并发升级。跨月/年方案切换必须展示其生效日和处理方式。
- 同周期升级保持原月度锚点，补差批次与当前基础批次同时到期；报价绑定订阅版本、价格版本、额度公式和当前账期，跨账期或版本变化后失效重报。
- 首版实现同周期等级升级的报价与差额发放；跨月/年转换可配置为下一续订周期生效，避免未经用户确认自动改写已付年费。
- 加量包有独立商品、额度数量和有效期，不受会员每月重置直接清零。建议初始为购买后 12 个月有效；该值属于待确认商业默认，未发布前不能对外销售。
- 额度耗尽拒绝新的收费模型请求并提供升级/加量包入口。自动购买加量包默认关闭；不能把自动续费授权解释为自动买包授权。

## 5. 资金和请求流程

### 充值与会员购买

外部支付通知校验签名、商户、订单、币种、金额和支付终态。浏览器跳转不能当作到账依据；同一支付交易只入账一次。

直接充值向指定产品现金账户入账；统一钱包充值向统一现金账户入账。购买/续费会员时先使用该产品现金余额；不足部分仅在存在有效统一钱包补款授权时补入。补款和购买扣款采用同一账本交易，余额不足则整体拒绝。

一次实际外部收款、一次内部划拨、一次会员消费分开记录；充值统计不能把内部划拨再次当作外部收款。

### 模型调用

1. SuperWagie/AgentWiki 发起平台模型请求，持有目标为 llmrouter 的短期、受限访问凭证，选择个人或团队付费账户，并提交稳定业务幂等键与请求摘要。
2. llmrouter 验证身份、成员资格、来源产品和允许的模型，持久化唯一 `logical_call_id` 与费率快照；同幂等键不同摘要拒绝，同一业务调用的供应商重试使用不同 `attempt_id`，不创建新的用户扣费调用。
3. llmrouter 通过受限服务接口向 UniHub 预占该付费账户的 **llmrouter 模型额度**，记录来源产品仅用于报表。
4. 预占成功后请求上游模型；最终真实用量由 llmrouter 报告，UniHub 按已登记的费率版本验证并结算，释放未使用预占量。
5. 结果不明时保留冻结并查单，不新建请求重复扣费。请求终态、用量终态和额度结算分别记录。

UniHub 的已发布费率版本是用户额度折算的权威；llmrouter 读取并在预占时锁定该版本，回报标准化的 input/output/cacheRead/cacheWrite/reasoning 数量以及供应商成本。各模型费率须明确计数口径是否互斥，避免缓存/推理 token 重复相加。UniHub 仅接受被授权的 llmrouter 服务身份回报，按相同版本独立复算；同一次 `logical_call_id` 只能形成一个最终结算。计算采用定点有理数，分项求和后一次向上取到额度最小单位，重复中间事件不重复取整扣费。

平台接入流量启用新的资金/额度适配器，不能同时再扣 llmrouter 原有本地用户 quota。旧的独立用户流量在 llmrouter 自身产品入口迁移前继续原路径，两条路径有明确标识。

模型上游成本与向用户消耗的模型额度分开存储；重试不能重复扣同一业务调用。首版建议无有效模型输出的纯供应商失败不消耗用户额度，平台承担供应商可能产生的成本；已有部分输出的取消按确认用量结算。缺失用量进入异常队列，不接受客户端自行声明的最终费用。

预占量及上游 max_tokens 限制控制单次风险；超过预占量时需先申请追加额度才能继续受控调用。流式输出及供应商最终计量差异可能产生有限超出，不能因此让用户额度为负；超出部分作为平台差异记录待处理。

## 6. 幂等、授权与恢复

- 授权用途分离：自动续费、统一钱包补款、自动购买加量包。每项绑定付费账户、目标产品、金额/额度上限、有效期和版本。
- 账务操作状态：`CREATED → SUBMITTING → APPLIED / REJECTED / UNKNOWN`；尚未提交可 `CANCELED`。
- `UNKNOWN` 必须使用原业务引用和幂等键查询/重放；未确认前不释放限额、不再次扣款、不发权益。
- 业务状态与 Formance 不构成分布式 ACID 事务。PostgreSQL 保存不可变命令与 outbox，Formance 是资产分录权威，恢复任务对齐两端结果。
- 撤销授权与任务进入 SUBMITTING 使用同一串行化边界。已开始提交的操作继续查单恢复，界面明确显示在途订单；撤销阻止后续新的执行。
- 对同一付费账户串行化资金策略执行；账本的余额检查为最终防线。价格、额度、团队成员权限在执行前复验。
- 权益状态独立于支付：付款成功、权益待发放不能显示为未付款或再收费。权益事件携带固定区间、唯一 grant ID 和版本。
- 退款采用追加分录和额度撤回，不删除原流水。购买撤销回购买时的钱包资金分配；外部充值退款回原支付交易，两者不是同一操作。订单保存实际分摊、已退款和可退上限；独立的历史统一钱包转账不因后续消费退款自动撤销。
- 退款先冻结目标订单来源批次的新预占；已有在途请求须结算/释放或转人工处理，冻结额度不能视为未使用。已消耗额度的订单不自动批准全额退款，进入带理由的运营处理。退款决定、权益调整、额度撤回和退款付款通过持久化状态机恢复；支付退款重试沿用同一操作，不因暂时失败重新发额度。
- 退款、额度撤回和迟到的权益发放按同一订单版本串行化，避免退款后消息重新发额度。

## 7. 账户与管理界面

用户中心第一层始终显示当前付费账户。主要页面：账户概览、产品会员、模型额度、加量包、钱包与充值、账单、自动设置、团队成员。

模型额度页区分本月套餐额度与加量包额度，展示到期日、冻结额度、来源产品及实际调用来源；不得把额度标记成可退款现金余额。

运营后台与用户中心使用独立客户端和角色。运营后台提供产品配置、计划版本、价格/额度、用户与团队、订单、充值、模型消耗、异常队列及审计。财务调整走追加账务命令并填写原因，不允许直接编辑余额。

页面采用中文优先、桌面表格型控制台，手机可完成查询、充值和授权。技术架构信息仅出现在运维设置，不暴露到普通用户购买流程。

## 8. 产品接入边界

### SuperWagie

现有实例密码、passkey、设备配对保持各自职责。平台登录使用独立 OIDC Authorization Code + PKCE 会话，桌面回调与 connect 配对分开；平台 token 不能写入 runtime bearer。桌面刷新凭证进入操作系统保护存储。

增加平台账户、个人/团队选择、会员权益、llmrouter 额度、收银台和平台模型入口。自带模型配置仍由原产品负责；平台额度校验在 llmrouter 服务端执行。客户端 session.stats 只用于展示，不能作为扣费凭证。

### AgentWiki

保留本地 User、Space、API key 和 AgentGrant。增加外部身份映射及 Space/任务到付费账户的关联；Space 不是企业账户本身。REST 与 WebSocket 都需验证绑定身份。页面权限与会员权益共同约束访问。

平台模型经 llmrouter 统一扣额度；任务入队时固定付费账户。现有聊天结果未完整保存 usage/cost，不能通过历史聊天回算收费。

### llmrouter

先新增受限 UniHub 额度预占/结算适配器供 SuperWagie 平台模型路径使用；保留其现有供应商适配和费率计算能力。作为第三个产品再接入自身 OIDC 用户入口、旧账号/余额迁移及独立产品门户。

### 后续产品

璇玑、灵犀、虾说按统一产品注册、OIDC、会员权益、收银台、llmrouter 调用契约接入，不为每个产品复制一个账务服务。

## 9. 实施切片与验收

本节均属于第一阶段：自有产品的账户与商业服务。以 SuperWagie 完成首个真实闭环，再按已确定顺序复用到其余产品。llmrouter 从首个闭环起提供模型服务。

1. **账户与资金基础**：Casdoor 接入、个人/团队、产品登记、钱包/账本适配器、审计、服务凭证；本地测试支付闭环。
2. **订阅与额度**：月/年套餐、逐月发放、加量包、报价升级、自动续费、批次消耗、退款恢复及用户中心。
3. **首个真实产品闭环**：SuperWagie 平台登录/会员/支付入口 + llmrouter 真实模型适配路径；通过故障恢复后才配置真实收款。
4. **后续产品复用**：依序 AgentWiki、llmrouter 自身产品、其他产品。

必须验收：

- 同一用户的个人、团队 A、团队 B 资金与模型额度不能互相读取或透支。
- 统一钱包 100 元、两产品并发各需 80 元，只能一笔成功；失败无部分扣款。
- 付款成功后进程崩溃、重复通知、恢复重放只产生一次订阅及一次当月额度。
- 年付只发本月额度；定时任务重复/漏跑、月末/闰年、时区变化不多发。
- 年付最后一期、闰日锚点、迟到补跑均不越过已付服务区间；同月两次升级各只发应补差额。
- 升级不重复发整月额度；降级和到期不把已消费额度重新释放。
- 套餐月底过期与模型调用并发，预占额度正确结算，剩余过期，不复活。
- SuperWagie 和 AgentWiki 并发调用只消耗同一付费账户的 llmrouter 额度；不扣两个产品现金钱包。
- 额度不足不自动扣现金买包；统一钱包充足但没有有效额度时仍拒绝模型请求。
- 退出团队、撤销授权、降低预算与任务并发符合已声明的执行边界。
- 已扣现金但权益发放失败可恢复；退款后迟到事件不能重新发会员或额度。
- 退款与跨产品在途调用并发时，先锁定来源批次，正确处理冻结量，不出现全额退款后迟到消费。

## 10. 发布前商业配置与验证边界

后台支持配置，但当前不编造：套餐名称/价格、包含模型额度、团队席位策略、加量包规格与有效期、同周期升级报价公式、退款条件、自动充值阈值和限额。默认所有真实销售商品处于草稿。

本地测试支付与真实商户支付严格分环境。真实收款前需选择渠道并配置商户信息、验证签名、退款、对账和回调恢复；完成代码测试不等于真实商户验收。

现有用户资料、真实余额和产品生产部署不在首个开发切片中自动迁移。迁移时必须验证旧账号归属、冻结切换点并形成期初流水。

本机具备 Go、Node、PostgreSQL CLI 和 Docker 客户端；初查 Docker daemon 未启动。该运行条件是验证前要处理的环境问题，不是设计已实现的证据。

## 11. 后续扩展边界

第二阶段建设第三方账户连接：用户或企业连接外部服务账户，管理多账号、授权范围、凭据生命周期及 Agent 使用权限。第三阶段在此基础上接入第三方 MCP 与 API，统一发现、访问授权和调用审计。MCP/API 的内部实施顺序尚未指定。

首版通过稳定的用户、团队、产品标识，以及独立的身份、权益、资金接口保留扩展空间。第三方连接与登录身份映射分别建模；企业账务权限不自动授予第三方资源访问权限。首版暂不建设连接器市场、凭据托管、通用 MCP/API 网关，也不预设第三方服务收费政策。

候选项目与后续决策事项见[扩展路线与调研](../../extension-roadmap-2026-10-24.md)。Composio、Nango 当前仅为研究候选，尚未选定、安装或接入。
