# UniHub 重建实施计划

以新的 UniHub 仓库和 113 上的新服务作为交付基线。从主分支拆出独立可回滚的 PR。每个 PR 用对应的端到端验收覆盖最新提交。集成和双区部署全程使用可免费自托管的开源组件。所选业务路径须能在没有商业软件许可证和付费版本的环境中跑通。

**实施顺序为方案修订与复审、与用户共同设计 UniHub UI、设计审核、编码。** UI 共创时覆盖个人与企业付款账户、席位、应用商品配置、钱包与充值回跳、目录和 Key。设计审核通过后启动 2a 及后续编码。阶段一已有本地验收记录。

LLMRouter 按渠道官方计量及渠道或模型倍率提供第一层基础金额，UniHub 以第二层溢价或折扣换算积分售价。UniHub 发布版本固定允许的路由和网关费率版本。**[拟议默认]** 以百万分之一积分入账，UI 共创确定展示精度。门户与网关 `/v1/models` 共用 UniHub 的发布及授权结果，网关提供可路由模型、计量元数据及统一模型 Key。[后台接口与计量核验](../../integration-api-assessment.md)

| 顺序和责任组件 | 实现范围 | 验收 |
| --- | --- | --- |
| 1. UniHub 和 Logto | 新门户、OIDC、服务端会话撤销、应用登记、个人与企业账户。阶段一企业级 `has_seat` 用于本地验证。 | `6b8483f` 在真实 PostgreSQL 和本地签名 OIDC 测试服务通过六组测试。113 的真实登录退出和分支合入待验收。 |
| 2a. UniHub 商品、目录和售价 | 按应用、账户类型、地区发布商品、模型能力与 UniHub 售价。定义应用席位契约、版本 ID 和快照接口。 | 两个应用各发布个人与企业商品。发布快照不可变，按生效时间唯一解析，按 ID 回读历史版本。用目录接口样例验证应用、账户类型、地区隔离及计量映射。 |
| 2b. UniHub 计费模块 | `src/billing/` 承接钱包、订单、席位、现金与积分。钱包扣款、待发放记录与确认订单同事务。 | 充值回原结账，重复支付回调只入账一次。新版本发布后保留原订单价格，恢复时按订单快照发放。应用席位并发分配受已购数约束，移除 A 席位不影响 B。核对现金、积分守恒。 |
| 2c. SuperWagie 首套商品 | 发布第一套个人与企业商品。以第二个应用验证配置复用。 | 验证月付、年付、月转年、升降档、取消自动续费、企业增减席、独立积分包到期，以及连续升级和在途补返。 |
| 3. 新 LLMRouter 和 UniHub | 接入统一 Key、同源目录、文本向量、重排序、豆包文生图、阿里 VL embedding、PaddleOCR，以及版本化预扣、结算与巡检。 | 按所选渠道官方计量逐条对账。改第一层倍率或第二层售价后，已预扣调用仍按原授权尝试的两层快照结算。验证异常场景和 SSE 恢复，对比相同渠道首包 P95。 |
| 4. 部署与升级演练 | 每区独立 Logto OSS 与 `LOGTO_ISSUER`。校验身份签发方及 CNY/USD 账区部署，演练网关兼容和源码发布。 | 双区各完成登录、支付、发放、调用和退款。异区身份、Key 与回调均拒绝。新版接新流量，旧版完成在途任务。按运行版本核对源码、`NOTICE` 和署名。 |
| 按需接入 Lago OSS | 根据企业出账需求，用开源版账单接口同步 UniHub 已确认订单。 | 在没有 `LAGO_LICENSE` 的实例验收新购、续费、增购样张。Lago 恢复后可补出账，门户账单和资金流水一致。 |

阶段一的门户、登录、退出与健康入口已通过本地验收。默认绑定回环地址。OAuth 客户端配置和会话密钥由部署环境提供。

**[待产品确认]** 2b 前确定退款、拒付、欠款、成员消费周期、邀请和应用权益接口口径。阶段 3 前确认低余额裁剪、同步证据和渠道重试。**[待联调核验]** 按渠道发布版本验证所选产品的计量字段和可执行上限。

## 账务与升级验收用例

| 触发条件 | 预期账务及可观察结果 |
| --- | --- |
| 两名有权成员同时消费，企业池或成员周期限额只够一笔。 | 只接受可覆盖的请求。批次按 `(expires_at ASC, batch_id ASC)` 加锁和扣减。企业池和成员周期均可回读原在途预扣。 |
| 网关调整倍率，UniHub 尚未更新对客售价，或调用期间两层价格改版。 | 2a 验证发布版本固定允许的网关费率。阶段 3 拒绝未发布版本报价，按已发布版本接受新预扣，按原授权尝试快照结算。 |
| 小额向量请求按渠道口径计为 0.05 积分。 | 阶段 3 结算为 50,000 个百万分之一积分单位，分项累计后只取整一次。账户流水和结算对账保留相同精度。 |
| 统一 Key 请求模型目录和不同能力。 | 同一应用和付款账户的门户与 `/v1/models` 结果一致。跨应用及停用路由拒绝，对所选渠道的 Token、图片或页数逐笔核对。 |
| 预扣不足以追加，或渠道实际用量超过已授权上限。 | 追加审核失败时不扩大上游用量。若已出现超额，用户消费只结算到已授权预扣，独立记平台差异，账户余额和周期上限不透支。 |
| 网关在提交前退出，异步受理后失联，或结算回执丢失。 | TTL 触发巡检，凭原请求号查询。确定未提交可释放。受理或用量不明进入核查，到证据截止按核验金额结算和释放。迟到证据只进平台对账。同一终态重试只入账一次。 |
| 流式期间重启 UniHub，原任务期间移除成员或跨账期完成。 | 已授权预算内响应继续，待发送终态在服务恢复后回放。旧会话和 Key 不能发起新企业消费。可信网关用原预扣结算或释放，扣原预扣周期。 |
| 钱包购买已扣款，发放任务尚未运行时进程退出。 | 恢复后由待发放记录补发权益，按原订单及周期去重。现金只记原扣款，账务和权益均可核对。 |
| 国内和美区的 Key、支付回调和计费请求双向混用。 | 交叉请求拒绝，错误地区和币种均无账本变化。两区正常路径各有可核对的订单和扣费流水。 |
| 网关新旧版本滚动共存。 | `/internal/billing/v1/` 按身份及 `gateway_version` 接收兼容请求。旧任务跨版本继续结算，新请求进新版。排空旧待发送记录后下线，已记账交易可回读。 |

用例定义为后续执行的验收目标。[实施方案](../../architecture.md)给出状态和退款口径。
