# Credit sales and payment readiness

`GET /v1/catalog` remains an array of the existing offer fields. Each response offer additionally has `sales_readiness: {ready: true}` or `sales_readiness: {ready: false, reason: "credit_rates_unavailable"}`. This is a transport view; immutable offers in orders, subscriptions and quotes have no readiness field or hash change. Component eligibility, environment and product-origin filtering remain in force. Unavailable offers stay visible so an unavailable catalog is distinguishable from an empty balance. Old servers may omit the additive field.

New positive-credit purchases, upgrade quotes/acceptance and renewals require at least one usable configured CREDIT/6 model tariff. Missing/failed reads fail closed; HTTP errors are `409 {"error":"credit_rates_unavailable"}` for known unavailable coverage and the existing `503 service_unavailable` for read failures. Readiness is rechecked with the current profile inside the durable order transaction, holding the shared rate-catalog advisory lock and product row lock. No readiness transaction is retained across ledger calls. Drafting/publishing remains possible before tariffs are prepared.

The existing billing selection/validation rules apply: nil model lists are unrestricted; empty lists deny all; model IDs match exactly (`*` has no wildcard meaning). The rate SQL status and snapshot status must both be published, asset must normalize to CREDIT/6, price terms must validate, the complete model/asset tariff set must be unambiguous, and an operation must map to an enabled wire. Managed video does not qualify. Multiple distinct operations are allowed; zero-priced valid terms are allowed. Default cash funding does not suppress explicitly configured credits. This prospective product-level check does not promise every model or upstream health.

Zero-credit subscriptions, existing credits, paid grants/monthly issuance, refunds and reconciliation retain their original terms. Original-key purchase/upgrade/renewal replays resume persisted orders even after rate retirement; current authorization checks still apply. No automatic cash fallback or conversion is introduced.

Admin `/admin/v1/system-status` now exposes `payment_mode` (`disabled` or `sandbox`), `sandbox_signing_configured`, and `real_payments_configured: false`. `payment_configured` remains a deprecated compatibility alias for sandbox signing readiness only. Merchant/signing configuration does not establish real acquiring. A payment channel, merchant onboarding/credentials, approved commercial prices/model coverage and a real verified adapter are still required for real payments.
