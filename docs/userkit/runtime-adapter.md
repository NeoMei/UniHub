# Mature-product runtime adapter

An existing product keeps its original users, credential verifiers, OAuth providers, MFA, Passkeys, password recovery, API keys and product UI. UniHub owns the stable identity/account mapping, current final product authorization and final settlement. Products without a mature user system may build their own UI with UserKit.

For LLMRouter, keep the original local `user_id`. Bind it only after a verified original authentication or an explicitly reviewed import. Never merge accounts by email or username. `GET /internal/v1/product-runtime/identity/{local_user_id}` only looks up a binding; it never registers a user. Original authentication must complete every configured factor before `identity/authenticate` is called. Passwords, OTP seeds and private Passkey material do not leave the product. Passkeys retain the original RP ID.

The product server uses `UNIHUB_PRODUCT_RUNTIME_ENABLED=true`, `UNIHUB_ORIGIN`, `UNIHUB_PRODUCT_ID=llmrouter`, `UNIHUB_PRODUCT_INSTANCE_ID=default` and `UNIHUB_PRODUCT_RUNTIME_TOKEN`. Service credentials are private deployment configuration. UniHub fixes each token's product, instance and allowed operations. Ordinary tokens need `identity:register`, `identity:lookup`, `identity:authenticate`, `identity:lifecycle`, `identity:manage`, `identity:browser` plus the selected runtime operations. `identity:import` belongs to a separate reviewed migration credential and must not be enabled for the ordinary browser/runtime credential.

Registration is idempotent by the original local user ID and operation ID, and only receives normal default roles. An old administrator is imported through `ImportProductIdentity` with a reviewed batch ID, frozen snapshot digest, exact original role and permission overrides. A trusted migration manifest may name `central_user_id` to link an existing central account; UniHub verifies that the account exists and rejects conflicting subject mappings. Public registration cannot select this field. No funds are imported by identity registration. Funding cutover and legacy balance import are separate audited operations.

`AuthenticateProductIdentity` accepts a one-use authentication ID, completed method, authentication time and exact local authentication version. Evidence expires after 60 seconds; the returned central actor assertion lasts 120 seconds and is stored only as a hash centrally. The product's server may attest its already verified session/PAT with method `session`; a browser cannot select the actor. A management call carries that assertion in `X-UniHub-Actor-Authorization` in addition to the scoped service token. UniHub rechecks current user state, product state, target hierarchy and effective permissions. A financial account owner is not automatically a product administrator.

Use the complete reviewed manifest in [product-user-manifests.json](../../config/examples/product-user-manifests.json). `product_role` is the original product role: 1 ordinary, 10 product administrator, 100 product root. It is never a global UniHub administrator role. Only explicitly marked `native_baseline: true` roles contribute the native administrator baseline. A viewer/operator may project product role 10 for the original page guards while retaining only its own declared permissions. Assigning a viewer therefore never implicitly unions the native administrator grants. The role 10 baseline preserves the original native administrator grants, including user management and promotional credit adjustment, while channel secrets/sensitive changes and root settings remain separate grants. Role 100 covers the complete declared product permission catalog. A per-user override applies after the role baseline, including explicit denial. Unknown permissions are rejected. Delegated administration cannot grant a higher/equal product role or a permission the actor lacks. Replacing roles through the central user console or runtime API clears the previous adapter overrides and product-role projection, so revocation cannot resurrect an imported root role.

Credential changes increment the original authentication version and write a local outbox event in the same database transaction. The restricted `identity/lifecycle` operation advances only that version by one and invalidates old actor assertions; it cannot create/enable users or grant roles. A failed central notification remains pending, is replayed idempotently before further authentication, and prevents local fallback. A current central denial, expired assertion or unavailable authority blocks protected work; no old local privilege or local wallet is used as a fallback.

The original login/registration forms and APIs remain the entry points. An existing central SSO session may be attempted once through `/api/unihub/login?prompt=none&return_to=<safe-local-path>`. State, nonce, PKCE, browser binding and return destination are checked server-side. Interaction-required or unavailable SSO returns to `/sign-in?unihub_silent=done&redirect=<safe-local-path>` without replacing the product form or redirecting in a loop. `/api/user/self` returns the same complete original user shape, current central role/capabilities, and the selected account's spendable balance for both authentication sources.


The runtime service template is [product-runtime-services.json](../../config/examples/product-runtime-services.json). Its token strings are placeholders, not credentials; replace them privately. Load the JSON with `PRODUCT_RUNTIME_SERVICES_JSON`. The reviewed-import credential has a distinct operation allowlist and is never sent to the browser. The public product client must enable `browser_sso`, register exactly one `/api/unihub/callback` URL, and declare its exact origin. Set `UNIHUB_PRODUCT_CLIENT_ID` and `UNIHUB_PRODUCT_REDIRECT_URI` on the product; runtime mode reads these browser settings without requiring the old OIDC authenticator. `UNIHUB_ORIGIN` supplies the central browser/API origin. An optional `UNIHUB_PRODUCT_OIDC_ISSUER` retains the existing Casdoor OIDC direction.

After all native login factors succeed, the product starts a three-stage browser handoff. The source stores an opaque flow bound to its verified original session and a short HttpOnly SameSite=Lax callback cookie. UniHub first creates an anonymous browser challenge, returns to the exact registered source callback, then accepts approval only from that product's service plus a fresh actor assertion. The source verifies its own cookie/state and live session before approving. UniHub consumes the challenge only in the browser that began it and creates the normal central `unihub_session`. This does not create a Casdoor password or replace the original product authenticator.

A second product can now use `/auth/product/authorize` with state, nonce and S256 PKCE. Its server exchanges the one-use code using its scoped service credential. The returned `ubp_` proof is valid only for one matching runtime binding operation; it is neither an OIDC token nor a general API token. The product reuses an existing canonical mapping or creates one ordinary local account, then issues its original full-lifetime product session. Each protected request still rechecks current central authorization. With no central session, the existing OIDC prompt-none attempt occurs at most once and failure returns to the original form. Browser handoff and authorization codes expire after 120 seconds; source credential-version changes revoke the derived central browser session.

A newly created native user's durable `product_registration_pending` marker is committed with the original user row and remains set across identity binding until funding activation and any signup-award receipt are confirmed. Login and self-read resume an interrupted registration. Existing imported users have no such marker and never receive signup activation. A failed authority or funding response leaves the marker pending and blocks completion; identity mapping alone is not a completed registration.

Original management routes declare resource read/write grants, with specific channel-secret grants retained. An unknown management route is denied for managed sessions until declared. Native role replacement resets the old role list and overrides to defaults plus the selected native baseline; custom grants must be explicitly reauthorized. New effective grants must be a subset of the actor's current permissions, so an explicitly denied root permission cannot be delegated indirectly by promoting another user. Managed API-key channel selection uses current central role and `channel:operate`, and keeps the original key's model/IP/group restrictions.


Codes and binding proofs retain the source binding and authentication epoch. Exchange, proof verification and final consumption recheck that source, so a credential change also rejects an authorization already in flight. Refresh-cookie rotation is returned immediately before central calls; an unavailable central response still denies work while preserving the browser's current refresh credential for retry.

The central account page reads a native account's canonical name and email and identifies its original credential manager. `account_settings_url` may declare an exact URL on the client's registered origin (LLMRouter uses `/profile`). Password, MFA, Passkey and original profile edits remain on that product's original page. The central page presents that link instead of sending native passwords to Casdoor; direct unsupported credential changes return `credentials_managed_by_product`. Accounts with a linked Casdoor identity select that exact configured issuer for the existing central credential flow.


The financial adapter also requires `calls:reprice` for accepted final-usage top-ups and post-result fee corrections. These operations carry an immutable parent call or the existing accepted call; they cannot admit another supplier request. Credential expiry/revocation blocks new use while the original payer/key/price remains responsible for already accepted usage. Insufficient available money stays pending for reconciliation and funding; no local wallet or artificial award pays it.
