# 两种产品接入方式

UniHub 统一身份目录、当前授权和最终资金账本。产品保留自己的用户资源、功能、计量和价格计算。接入方式取决于产品是否已经有成熟用户系统，不取决于用户从哪个入口登录。

| 产品情况 | 接入方式 | 用户体验 |
| --- | --- | --- |
| 已有成熟用户和资金账号 | 保留原用户 ID、认证器、API Key、资金账号、资源与历史，通过受信任适配器建立映射 | 原登录注册、用户管理、额度、Key、监控和功能页面照常使用 |
| 尚无完善用户系统 | 引用 `packages/userkit-go` 源码，完成自己的 Provisioner 和产品权限声明 | 使用自己的产品界面，复用 UniHub 身份、授权、会话及结算能力 |

同样角色、资源、配置和资金条件下，两种身份来源必须得到同样的产品能力。首次进入产品时执行产品原有的新用户策略；已有映射不重新发放赠送额度或默认 Key。

## 成熟产品

1. 原产品完成密码、OAuth、MFA、Passkey 等全部认证因素。
2. 适配器按原 `local_user_id` 查询、注册或采用经验证的中央绑定。已有账号之间的合并必须单独审核，邮箱相同不构成绑定证据。
3. 原页面调用原 API；后台从 UniHub 读取当前产品授权。中央管理员、产品管理员、财务管理员是不同授权，不自动互相继承。
4. 普通 Key 仍使用原用户、分组、模型、IP、有效期和限额规则，调用仍走原路由、计量和价格计算。
5. 产品冻结调用的付款账号和价格快照，通过统一结算接口预留、补足、结算、释放和退还原调用资金。已经确认的消费义务可恢复，不能因为断线重发供应商请求。

完整认证、浏览器会话及配置协议见 [runtime-adapter.md](runtime-adapter.md)。

## 新产品

参考 `packages/userkit-go/examples/minimal` 实现 `Provisioner.Ensure`：用中央 issuer/subject 的唯一键创建或复用自己的业务用户，保存产品用户 ID；在业务用户上增加产品自己的资源、设置及权限字段。唯一键必须由数据库约束保护，不能用姓名或邮箱替代。

使用同一源码包的 `RuntimeClient` 接入中央浏览器授权、当前产品权限与资金接口；用产品 manifest 声明角色、资源和读写权限。产品的后端保存 service credential，浏览器只持短期单次授权票据或本产品会话。没有余额或计费需求的产品无需实现资金适配。

当前资金实现专用于 LLMRouter 的 `LR_QUOTA/0` 及实例隔离。其他产品可以直接复用身份、授权和浏览器接入组件；接入计费前须显式声明资产、单位和价格适配，不会自动获得 LLMRouter 额度或隐式转换货币。

`Provisioner` 只负责产品用户和资源初始化。产品首次注册奖励、默认 Key、套餐权益等仍由产品策略决定；中央注册和资源初始化需要分别可重试并防重复。

## 资金与旧账号

管理员原来的“增加额度”继续增加该 LLMRouter 实例的可消费额度，资产为 `LR_QUOTA/0`，单位版本 `lr-quota-v1`。它不是提高预算上限，也不自动成为其他产品可消费的现金。产品订阅是已经购买的产品权益；套餐内消费不能再扣一次钱包。

旧账号可以先只映射身份，原资金后端保持原所有权。余额切换需要单独审核和一次性账本导入，不能随着 SSO 登录自动搬迁。导入之前必须完成外部停机盘点、旧批量账核对、缓存与 SQL 核对，以及未终态调用和退款责任核对。

LLMRouter 的 `product-runtime-migrate` 默认只校验快照。资金导入额外要求 `offline_evidence`：全写节点停机声明、批量及缓存核对声明、备份 SHA256、规范化用户快照 SHA256 和证据引用。`drained: true` 单独不够。命令先核对整批用户，再进行远程变更。证据被写入原始导入回执，重复或更改证据不能重新导入资金。

这些声明是操作方提供的外部审计证据。CLI 不能自动证明旧版本节点已经退出，也不能凭备份哈希证明备份已经还原成功；本地互斥锁只能保护本进程。正式迁移须实际取得停机和备份还原验证记录。未获得记录时仅做身份映射，不运行资金导入。

余额充值保留原支付订单，再用可恢复收据交付中央额度；原页面区分支付确认与额度入账。外部直接购买订阅保留原订阅订单和支付收入凭证，不伪造成钱包充值。真实支付渠道收款、外部供应商结算和生产迁移各有独立验收。
