# UniHub 架构设计说明与评审指引

评审基线为 2026-11-26 的新 UniHub 方案。本文说明选型和设计取舍，业务流程与交付阶段见[开源集成实施方案](architecture.md)。

## 目标和已确认的业务要求

- **使用体验。** 用户和接入应用都通过 UniHub 登录、选付款账户、充值、买会员与积分、获取模型与 Key、查用量和账单。三个后台的管理入口供运维使用，推理和认证通过 UniHub 品牌入口承接。
- **架构。** UniHub 统一维护应用、商品、订单、权益和账本。个人和企业分别结算。企业在应用内共享积分池，可为成员设置周期消费上限。每次扣费都有可追溯的付款账户、请求编号和费率版本。
- **升级与成本。** 以 113 上新部署的 Logto OSS、Lago OSS 和 LLMRouter 所对应的源码版本为基线。采用可免费自托管的开源代码并履行适用许可证义务。国内 `cn/CNY` 与美区 `us/USD` 复用同一套程序，每区部署独立 Logto OSS、独立账本并配置各自的 `LOGTO_ISSUER`。
- **商品。** 采用调研过的 WorkBuddy 订阅、席位、积分包、升级和使用扣减流程。SuperWagie 提供第一套商品配置。后续应用通过卡片数量、文案、价格、积分数量、有效期和费率参数发布自己的商品，执行同一套业务逻辑。[WorkBuddy 套餐管理](https://www.workbuddy.cn/docs/workbuddy/Plan) · [WorkBuddy 企业版计费](https://cloud.tencent.com/document/product/1831/134334)

## 方案比较

| 方案 | 用户体验 | 架构与运行代价 | 跟随上游 |
| --- | --- | --- | --- |
| 三个后台都通过原有 API 集成 | 可以统一门户。流式中断、异步任务和失败退款的扣费状态仍缺少可靠的来源。 | UniHub 仍要实现付款账户、权益和积分并发控制。代理或日志轮询无法单独补齐模型终态。 | 原版服务最容易升级，外围需补用量恢复能力。 |
| **UniHub 自建业务核心，复用认证与网关，Lago 按需出账** | **用户看到一致的账户、商品、支付和用量。** | **UniHub 持有业务账本。LLMRouter 在已有请求和任务生命周期里提供计费用量。Lago 故障与交易链路隔离。** | **Logto 和 Lago 使用原版接口，网关维护一组集中、可回归验证的接入改动。** |
| 参考三个项目全量重建 | 体验可按产品需求定制。 | 另需维护认证安全、模型协议、流式、渠道故障与异步任务的通用能力。 | 上游协议更新、缺陷修复和新功能要自行移植。 |

选择中间方案。体验上的定制集中在 UniHub，账务一致性优先于减少网关改动，网关改动的维护成本用真实上游升级演练衡量。

## 关键设计及原因

### 1. 原版 Logto 提供身份，UniHub 决定业务权限

复用 Logto 的 OIDC 登录、账号找回、MFA 和密钥轮换。UniHub 用 `issuer + sub` 识别登录身份，通过业务账户和角色决定谁可购买、授权或代表企业消费。这样登录方式变化也不会改变付款账户归属。首期采用 OSS 标准登录体验和品牌 HTTPS 入口。当前版本整套自定义登录页上传有自托管授权检查。[Logto 部署配置](https://docs.logto.io/logto-oss/deployment-and-configuration) · [v1.46.0 自定义登录页检查](https://github.com/logto-io/logto/blob/v1.46.0/packages/core/src/routes/sign-in-experience/custom-ui-assets/index.ts#L94)

阶段一已经实现服务端会话撤销和企业成员权限检查。阶段一以企业级 `has_seat` 验证资格。接入应用级付费权益后，**[拟议默认]** 以对应企业、应用与订阅下的实际席位作为权限依据，从而将单应用撤权限定在该应用下。已授权任务按原账户和周期结算。身份绑定沿用 `issuer + sub`，账区由 `deployment_region` 校验。[应用席位方案](architecture.md#按应用分配席位)

### 2. 商品配置按应用发布，所有应用共用计费模块

按应用、账户类型和地区发布不可变的商品与售价版本，统一购买、续费、升级、发放积分和消费流程。商品版本显式表达档期转换、积分发放与有效期、续费、席位与可供应用读取的权益。订单保存成交快照，模型调用保存预扣所用的两层费率和兑换版本。2a 单独验收版本发布、精确解析与回读，订单和模型快照在其各自阶段验收。**[拟议默认]** 首套商品规则以实施方案字段表为起点。[商品版本](architecture.md#商品版本要表达的规则)

升级返还沿用已核对的 WorkBuddy 基础积分公式，以旧订单实际支付金额分摊的当前期和未开始月份计算。当前期只按未用基础积分占比返还。这样先用掉临期积分包的用户仍可获得旧套餐剩余价值，已用的套餐基础积分也有可复算的金额。返还进原 UniHub 付款钱包。连续升级逐个旧订单封账，在途用量最终确认后，按同一公式补付差额。[折算公式与样例](architecture.md#个人套餐升级折算) · [WorkBuddy 升级说明](https://www.workbuddy.cn/docs/workbuddy/Plan)

### 3. UniHub 是唯一的资金和积分写入方

首期把订单、会员、席位、现金与积分流水放在同一个 UniHub 服务和 PostgreSQL 中，方便用事务约束购买、发放和预扣。购买付款与待发放记录同事务提交，后台按订单及权益周期重放。预扣同时锁定企业池和成员周期用量，按 `(expires_at ASC, batch_id ASC)` 锁批次。现金和积分各用固定精度整数，每日核对守恒关系并检查长挂预扣。固定锁顺序减少并发交叉等待，幂等与对账结合可以发现支付成功后漏发、在途金额未释放等问题。

### 4. LLMRouter 局部接入请求计费和异步终态

品牌反代把模型正文、流式响应和任务查询交给 LLMRouter。UniHub 校验付款权限并管理对客 Key 流程，LLMRouter 签发、保存和验证同一模型 Key，为 embedding、rerank、豆包文生图、阿里 VL embedding、PaddleOCR 等路由提供统一入口。网关提供可路由能力，UniHub 集中解析门户和 `/v1/models` 的可见目录。UniHub 重启期间，已授权流式用量仍可传输，终态进入网关持久化待发送记录。

LLMRouter 按实际渠道的官方计量与价格、渠道或模型倍率得到基础金额。UniHub 按应用和账户类型应用溢价或折扣，再换算为积分。UniHub 发布售价时固定该售价允许的路由和网关基础费率版本，因此网关调价在 UniHub 发布生效后才反映到用户价格。保留官方计价依据、基础金额与两层版本，能分别与渠道回执和积分账核对。**[拟议默认]** 以百万分之一积分入账，避免小额调用按一整点扣费。自托管 OCR 用部署成本配置基础价格，收费 OCR 按选定产品的官方计量口径。[多路由计量核验](integration-api-assessment.md#多路由计量核验)

请求先按可验证的上限预扣，实际超额的差值计入平台成本，用户结算额受已授权上限约束。这个方案按预付费要求处理渠道异常。`expires_at` 触发后台巡检，受理或计费用量未知时先查原请求。到证据截止时按已核验金额终结，未证实部分释放，迟到证据进平台对账。TTL 在这里用于恢复和核查，防止早放、重复派发与无限冻结。结算与释放以原预扣作为互斥终态。现有插件报告可能在队列过载或重启时丢失，正式计费使用可重投的持久化记录。[计费会话接口](llmrouter/relay/common/billing.go:7) · [任务终态](llmrouter/service/task_polling.go:681) · [插件报告语义](llmrouter/docs/plugin-api/v1.md:2745)

### 5. Lago OSS 从已确认交易异步出账

首期从 UniHub 账本生成订单明细和收款凭证。Lago OSS 的价值主要在标准账单 PDF、复杂用量计价或周期后付费。v1.57.0 的接口支持外部设定账单支付状态，实收流水仍需由 UniHub 保留。普通账单的手工收款明细和单个订阅动态席位数量覆盖需要 Premium。先用开源版验证企业账单样张和去重恢复，再决定是否接入。接入后，Lago 暂停期间，钱包、权益和模型扣费可继续。[账单更新接口](https://github.com/getlago/lago-api/blob/v1.57.0/app/controllers/api/v1/invoices_controller.rb#L342) · [手工收款](https://github.com/getlago/lago-api/blob/v1.57.0/app/services/payments/manual_create_service.rb#L74) · [席位覆盖](https://github.com/getlago/lago-api/blob/v1.57.0/app/services/subscriptions/update_or_override_fixed_charge_service.rb#L20)

### 6. 独立构建与落地验证

UniHub 与 AGPL 组件使用分仓、分进程和版本化 HTTP 协议，便于独立升级及提供对应运行版本源码。内网计费协议首版有明确版本，旧网关收尾在途任务，新调用切到兼容的新网关。部署隔离外，支付、Key 和计费协议均校验 `region + currency`，避免误配域名或凭证后串区。AGPL 运行版本源码和 `NOTICE` 作为发布检查项。[AGPL-3.0 第 13 条](https://opensource.org/license/agpl-3.0)

## 待定的实施参数

**[待产品确认]** 首期商品实际定价、续费与企业变配边界、退款拒付口径、支付通道和成员周期。**[待联调核验]** 各渠道实际产品版本、可验证用量上限、证据截止时间、升级目标和延迟指标。先复审实施方案，再与用户共同设计 UniHub UI，设计审核通过后启动编码。

## 请评审 agent 核查的反例

| 问题 | 建议用例与确认条件 |
| --- | --- |
| 应用、企业和用户权限是否绑定到同一笔交易 | 用一个应用的 Key 请求另一个应用的模型。让成员离开企业后用旧会话购买或发 Key，并发起新的模型调用。可信网关仍可结算其原有预扣，跨月使用原成员周期。 |
| 一套商品配置能否表达首批业务 | 用 SuperWagie 覆盖月付、年付、企业增购、积分包与升级折算。复算基础积分用尽、先用临期包、连续升级以及旧在途结算后的返还差额。用第二个应用只改商品卡、价格和数值跑同一流程。 |
| 现金和积分账是否在异常时仍可核实 | 重复、乱序或超时发送支付通知，以及一笔付款到账后进程在发放权益前退出。要可恢复原订单，且只入账和发放一次。验证两区的币种验签和同一付款账户跨应用购买。 |
| 网关能否完整交付计费事实 | 用统一 Key 覆盖指定路由，比对官方计量、倍率基础金额和 UniHub 实扣。覆盖并发额度、流式断连、超额、异步失联、渠道重试与结算回执丢失。先改价再结算旧请求，逐笔检查版本。 |
| 无商业授权时能否满足实际体验 | 无商业许可证环境跑通标准登录和所需的 Management API 操作。对 Lago OSS 核对实际账单样张、回写状态、金额和重复出账。把源码可见、接口可用和线上验证分别说明。 |
| 两服和上游升级是否能独立推进 | 双向交叉测试 CNY/USD 的回调、Key 和内网计费请求。隔离环境升级到真实上游版本，核对已有账户、Key、在途任务、未完成结算和运行版本源码，比较同一模型渠道的首包 P95。 |

评审意见按**阻塞问题、待验证假设、可优化项**返回。每条给出受影响的模块、可复现的失败场景、建议改动和验证方式。如建议改换组件，说明对体验、账务一致性和后续升级的影响。
